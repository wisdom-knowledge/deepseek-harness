# 会话状态及交付

## 状态保存

能写文件时，在当前工作区的独立 `task-interviews/<task-id>/` 中保存 `state.json` 和题目草稿；新题使用独立目录，已有目录先读取，禁止覆盖别题。不能写文件时在对话中提供可恢复摘要，不声称已保存。不要把专家信息写入全局skill目录。

状态结构按实际信息填充，不为了字段齐全编造内容：

```json
{
  "task_id": "example",
  "status": "信息待补全",
  "authorization": {"status": "待项目方确认正式使用范围", "source": null},
  "rule_version": "2026-10-19",
  "revision": 1,
  "brief": "专家的原始需求",
  "materials": [],
  "requirements": [],
  "economic_value_facts": [],
  "expert_steps": [],
  "interview": {
    "answered_rounds": 0,
    "current_questions": [],
    "pending_questions": [],
    "remaining_estimate": {"min": null, "max": null, "includes_current": true, "excludes_final_confirmation": true},
    "estimate_reason": null
  },
  "coverage": [],
  "requirement_changes": [],
  "open_questions": [],
  "conflicts": [],
  "verification_limits": [],
  "expert_confirmation": null
}
```

每份材料记录：ID、路径/上传名称、文件角色、实际格式、内容和用途、必要性、角色确认依据、读取范围、未读内容、资源依赖情况。可用时记录哈希用于识别替换。

每条要求记录：ID、文字、对应产物、来源类型、来源定位、确认状态、约束强度、核验方法、依赖材料ID。

每个待问项记录：ID、类型（开放/确认）、单一待获取事实或决定、已有依据、涉及字段、答案会改变的具体内容、不问的实际后果、为何不能复用已有信息、是否阻塞成稿、依赖的问题ID、回答状态。说不清用途或后果的候选不进入队列。同轮只选依赖已解决且彼此独立的问题，轮数按筛选后的分组批次估算。短答只关闭实际解决的项，不按轮次批量标成已答。`answered_rounds`不等于`revision`，文件更新和工具调用不计轮。续聊旧状态中的`current_question`时将其作为单项读取，不丢弃未答内容。

`coverage`记录重要内容的已知要求、明确不限定、未知或不适用状态，并关联来源和草稿位置。未知项注明是否阻塞及原因，不要求全部转成已知才成稿。已关闭主题如需重开，在待问项说明新证据，不能仅因出现同义术语重开。`requirement_changes`只在确有变更时记录旧值、新值、专家依据、受影响字段及确认状态，不把泛化回答视为所有旧约束的取消。

来源类型区分：专家明确回答、适用规则、明确作为规范的附件、材料观察、助手建议。材料观察和助手建议不能自动成为要求。即使来自附件，也要确认该附件及对应部分具有约束作用。生产通用规则不能被专家随意豁免；若要偏离则待项目方决定。

来源定位要可追回到具体回答或文件/页/对象，不写笼统“根据对话”。专家确认必须关联当前草稿版本；其后实质修改使旧确认失效。

## 给专家看的输出

展示前执行[成稿质量门槛](output-quality.md)，检查必要要求、字段职责及篇幅。能从已有证据修好的先内部修好，只有缺少必要事实才追加提问，不把“请专家自行完善”当成交付。经济价值还应基于已有岗位、工时及流程事实说明模型协作可以支持哪类工作，不能只介绍任务困难，也不能编造节省比例或收益。

默认仅展示动态剩余轮数和本轮少量互不依赖的问题，遵循[访谈节奏](interview-protocol.md)。开放题与确认题分轮。不每轮展示任务理解、写盘状态、已确认摘要或草稿；专家主动要求时可展开。必要的规则与材料限制在收尾集中简述，阻塞当前问题的限制即时说明。

最终固定输出以下三个独立字段草稿，便于分别填入提交表；不能把经济价值和做题步骤笼统归为附加信息：

默认输出已组织好的要点稿：prompt与经济价值用简洁bullet points，做题步骤用有序列表。每条表达一个完整、相关的要求或意思，不是关键词碎片或“请补充某项”的提纲；专家应只需调整表达，不必重新搜集、拼接信息。不要同时提供要点版和长文版。下述经济价值字数要求用于完整段落稿，要点稿不为凑字数扩写。

1. **prompt草稿**：角色与目标、软件依赖（无版本）、逐个输入附件的文件名、格式、内容与作用、逐产物要求及output目录。只有模型执行任务需要的信息，不包含实现路径、内部访谈与答案。
2. **经济价值草稿**：约50至200字，说明真实岗位及工作环节、人力耗时或成本、机械重复工作与专业判断。所有事实和估算均关联专家回答或经确认的依据，不能虚构收益、客户、频次、工时或费用。
3. **做题步骤草稿**：按输入到输出顺序组织专家提供或明确确认的关键动作、专业判断及易错点，完整连贯但无需罗列每次点击。计划与实际执行状态写在辅助说明中，不把计划伪装成已做过；验收要求不能只藏在步骤里。

有文件写入能力时可将三稿保存为同一份 `draft.md` 的三个明确章节，状态保存在 `state.json`。不必额外生成众多文件。

最终展示直接使用同版保存正文，不为聊天另写一版。确认绑定实际展示的三字段内容；若发现磁盘稿不同，先同步实际确认文本，不能只给旧稿盖“已确认”的状态。

软件版本、系统等meta以及详细材料清单保留在内部状态，专家要求时再展示。prompt本身仍须完整包含输入附件说明。必要的待确认与核验事项置于三稿之后，标明涉及哪个字段、需要谁确认什么；它们是辅助说明，不是第四个提交字段。不使用“请检查所有文件”之类泛泛提示。

三个字段均需经过访谈补全和专家确认才能结束成题。若专家提前要求草稿，仍按三部分输出，以明确的待补项标记缺失，不用泛泛套话填满，也不称为完整定稿。未经另行要求不生成评分权重、hard gate或完整rubric。

验收要点只能从已确认要求派生，不增加题面没有的约束。尚未确定的问题不混进最终指令，可在工作草稿里明确标为占位，但有占位就不能称专家已确认的完整题目。

## 典型交互判断

- “做一张海报，尺寸你定”：先问投放位置和是否有渠道规范；允许提出备选尺寸，不把建议直接写成硬要求。
- 上传一份成品PSD：“参考这个出题”：先确认它是reference还是待处理输入；不把完整成品直接放入input，不照抄全部设计参数。
- 正文音乐A，分镜音乐B：列明冲突，问是否同一文件别名或应修改哪份材料；不能自行选A。
- 专家只说“就照你的建议来”：可以确认紧邻且明确展示的建议，不算确认未展示的其他参数或未来推断。
- “都齐了，保证过审”：可报告已完成的内容与剩余边界，不承诺通过，也不隐藏疑点。
